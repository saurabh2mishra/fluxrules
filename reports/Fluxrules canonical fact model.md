# Facts Flow Flat; Hold the Adapter Layer

Facts reach the fluxrules rules engine through a single, well-defined channel: a flat `dict[str, Any]` where all keys are strings and all values are scalars. This is not an accidental constraint but a deliberate design, reinforced by a structural validator, a `Flatten` transform built explicitly for pre-processing nested data, and an evaluator that performs nothing but a direct `facts[field]` key lookup. A canonical multi-source fact model is achievable with modest additions — a `typing.Protocol` adapter interface, a field-normalization step at the adapter boundary, and an optional context envelope — and the existing `FactPipeline` infrastructure provides most of the plumbing already. The case against building it now is strong: no second real source type is in active use, the "rule of three" for abstractions has not been met, and premature interfaces in this area carry a documented risk of API churn during the first three months of a new abstraction's life. The right verdict is to park the full abstraction but add one thin preparatory step: document the expected adapter signature as a `Callable[[], dict | list[dict]]` so the first integration doesn't paint the design into a corner.

## All facts arrive as a flat dict through three layered entry points

Facts enter the engine through three points that progressively narrow the accepted type. `fluxrules.evaluate(rules, facts)` in `src/fluxrules/__init__.py` is the widest: it accepts a plain dict, a Pydantic v2 model (calling `.model_dump()`), or a Pydantic v1 model (calling `.dict()`). Below it, `RuleService.evaluate_ruleset()` and `evaluate_inline()` in `src/fluxrules/services/rule_service.py` accept only `dict[str, object]` — Pydantic coercion is assumed to have happened upstream. Deepest down, `EnginePort.evaluate(ruleset, facts)` in `src/fluxrules/engine/interfaces.py` defines the contract every engine must satisfy: it takes a `Ruleset` and a `dict[str, object]` and returns an `EvaluationResult`. A parallel stateful path — `BaseEngine` / `PhreakEngine` — loads rules once and accepts facts per call without a `Ruleset` argument, but this path is separate from the `RuleService` flow.

There are two noteworthy rough edges. Pydantic coercion is duplicated: `_coerce_facts()` in `__init__.py` handles it, and `ReferenceEvaluator.evaluate()` performs the same coercion independently, suggesting the evaluator predates the public API helper. More consequentially, the structural flat-contract validator (`FactValidator`, enforcing no nested dicts, no lists, all string keys) is opt-in, not default — it fires only when `strict_facts=True` is passed to `BaseEngine.evaluate()`. `RuleService`, `ReferenceEvaluator`, and the public `evaluate()` function never call it. A caller who passes `{"user": {"age": 25}}` will receive no error; the condition `field="user.age"` will silently return `False` because `"user.age"` is not a top-level key.

## The flat contract is intentional — and the `FactPipeline` is already the bridge

The evaluator logic in `src/fluxrules/services/reference_evaluator.py` and `src/fluxrules/domain/dsl/evaluator.py` both perform a single-level key lookup: `if field not in facts: return False; else evaluate_operator(facts[field], condition_value)`. `RuleCondition.fact` is typed as `str` — a plain string key, not a path expression. Dot notation in field names (e.g., `"user.age"`) is a naming convention produced by the `Flatten` transform, not a path syntax the evaluator interprets.

The existence of `Flatten` in `src/fluxrules/pipeline/transforms/builtin.py` — which converts `{"user": {"age": 25}}` to `{"user.age": 25}` — reveals the intended pattern: **raw source data (possibly nested) → `FactPipeline` with `Flatten` → flat dict → engine**. `FactPipeline` in `src/fluxrules/pipeline/core.py` supports sequence (`>>`), fallback (`|`), and conditional (`when`) composition. Built-in transforms — `Rename`, `FieldType`, `Defaults`, `Require` — handle the remaining normalization steps. `FactSchema` in `src/fluxrules/pipeline/schema.py` adds an optional Pydantic-based typed boundary; `.to_facts()` calls `model_dump()` then `FactValidator.validate()`. The infrastructure for multi-source normalization is largely in place; what is missing is only the source-adapter protocol sitting in front of the pipeline.

## A canonical fact model needs four pieces, three of which already exist

A full multi-source fact model for fluxrules requires: (1) a source adapter interface, (2) field-name normalization at the adapter boundary, (3) an optional context envelope for lineage, and (4) the transformation pipeline that converts adapter output to engine-ready facts. Pieces 2–4 are already implemented.

**The source adapter interface** is the missing piece. The lightest viable form is a `typing.Protocol` with two methods: `load() -> list[dict]` for batch pull sources (SQL queries, Parquet files, REST API calls) and `stream() -> Iterator[dict]` for event sources (Kafka, Kinesis). Python's `Protocol` enables structural subtyping, so an adapter wrapping a SQLAlchemy session or a PyArrow `Table` needs no inheritance ([Python Protocol Classes for Type Safety](https://oneuptime.com/blog/post/2026-02-02-python-protocol-classes-type-safety/markdown)). A `close()` method rounds out resource lifecycle. Async variants (`aload`, `astream`) belong only when the engine adopts an async context. The Microsoft BizTalk / Logic Apps rules engine codified the same split decades ago as `IFactCreator` (batch, one-shot, returns `object[]`) and `IFactRetriever` (incremental, called each execution cycle with a reuse token for caching) ([Azure Logic Apps Rules Engine docs](https://learn.microsoft.com/en-us/azure/logic-apps/rules-engine/build-fact-creators-retrievers)), which suggests the two-method split is well-validated across languages.

**Field-name normalization** belongs on the adapter, not in the engine. Each source returns native names — SQL column names, Avro field names, Parquet column names, JSON keys — and no Python data library performs cross-source normalization automatically ([PyArrow Table API](https://arrow.apache.org/docs/python/generated/pyarrow.Table.html)). A `field_map: dict[str, str]` parameter on each adapter, mapping source-native names to canonical fact field names, keeps normalization explicit and auditable. Avro introduces the additional complication that field resolution uses name matching, and a rename without an alias declaration breaks reader/writer schema compatibility ([Schema Evolution in Avro, Protocol Buffers and Thrift](https://martin.kleppmann.com/2012/12/05/schema-evolution-in-avro-protocol-buffers-thrift.html)), so Parquet and Avro adapters should read the stored schema at initialization and apply renaming once, not per record.

**The context envelope** is the lightest addition for observability: a `FactContext(source_id: str, ingested_at: datetime, schema_version: str | None, trace_id: str)` dataclass kept separate from the fact dict so rule conditions see only scalar fields. For streaming sources, partition/offset (Kafka) or sequence number (Kinesis) belong here too, enabling replay and deduplication. This lives outside the engine's evaluation contract — rules never reference context fields — making it pure infrastructure plumbing.

## One source active means the abstraction has no second consumer to justify it

The decisive argument for parking is the rule of three: wait for at least two real source types in production before introducing an interface, because an interface with only one real implementation forces every future reader to pay for an indirection nobody yet needs ([The Abstraction Tax](https://dev.to/utak3r/the-abstraction-tax-55mn); [Common Software Design Mistakes](https://www.codingshuttle.com/low-level-system-design-lld-handbook/common-software-design-mistakes)). Right now, fluxrules has one production source: flat JSON sent to the HTTP API (`EvaluateRequest.facts: dict[str, Any]`). One real-world post-mortem describes a team building a flexible data layer for many backends that ended up with one backend in use, a configuration object accumulating twelve special cases, and an abstraction wrapping a single fetch call — a directly analogous trap ([Useless Abstractions](https://nitesh.is-a.dev/posts/useless-abstractions)).

API churn risk is highest in the first three months of a new abstraction, and field-name normalization is the most likely source of that churn — exactly the dimension where adapter design is least settled and where practical requirements only emerge from real integrations. Introducing the abstraction prematurely in the engine core compounds this; placing it in a `fluxrules.contrib.sources` namespace (opt-in, explicitly experimental) keeps the core clean and signals that the interface is not yet stable.

The concrete trigger for building the Protocol is: **two distinct source types actively used in production or in real integration tests** — for example, a SQL source and a REST API source, both wired to real rulesets. Reaching that trigger probably also means `EvaluationSession.add_fact()` (the streaming accumulation path) will have seen real use, clarifying whether the streaming API needs a first-class `stream() -> Iterator[dict]` on the adapter or whether accumulating individual key/value pairs is sufficient.

The one preparatory step worth taking now: document the expected callable signature — `source_fn: Callable[[], dict | list[dict]]` — in a comment near `EvaluationSession` or `FactPipeline`, and resolve the duplicated Pydantic coercion between `_coerce_facts()` and `ReferenceEvaluator.evaluate()`. Neither requires a new interface; both reduce the friction when the second source arrives and the real design work begins.

## Conclusion

The current architecture is not a limitation — it is a feature. The flat-dict contract keeps the evaluator minimal and rule conditions readable, while `FactPipeline` already handles the transformations that multi-source data actually requires. The canonical fact model is well understood: a `typing.Protocol` with `load()` and `stream()`, per-adapter `field_map` normalization, and a thin `FactContext` envelope for lineage. Building it now, before a second real source forces design choices, risks creating an abstraction that serves no current user. The sharper move is to remove the one existing rough edge — duplicated Pydantic coercion — and to record the intended adapter signature so it is ready when the trigger condition (two sources in production) is met. Park the Protocol; clean up the coercion duplication; revisit when the second source arrives.
