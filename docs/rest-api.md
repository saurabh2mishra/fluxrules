# HTTP API Reference

**Prerequisites:** [HTTP API](api.md) (starting the server).

---

This page lists the main endpoints of the FluxRules server, with the request
and response of each. The server needs the `api` extra
(`pip install "fluxrules[api]"`). Start it with `fluxrules serve`.

The full, always current list is generated by the server itself: open
`http://localhost:8000/docs` while it runs.

## Endpoints at a glance

| Method | Path | Purpose |
|--------|------|---------|
| GET | `/health` | Health check |
| POST | `/api/v1/auth/token` | Log in and get a token |
| POST | `/api/v1/rules` | Store a rule |
| GET | `/api/v1/rules` | List stored rules |
| POST | `/api/v1/evaluate` | Evaluate one fact against stored rules |
| POST | `/api/v1/evaluate/bulk` | Evaluate several facts |
| GET | `/api/v1/explain/{execution_id}` | Look up an earlier evaluation |
| POST | `/api/v1/rules/simulate` | Dry run with explanations |
| POST | `/validate` | Check a rule set without storing it |
| POST | `/api/v1/sessions` | Create a session that stores facts |
| POST | `/api/v1/sessions/{id}/evaluate` | Evaluate each fact stored in a session |
| POST | `/api/v1/engines/evaluate` | Evaluate a fact, with an explanation per matched rule |

Each one is described in full below.

## Basics

- Requests and responses are JSON (`Content-Type: application/json`), except
  the login form below.
- Rules are stored in the server's database. Add them with
  `POST /api/v1/rules` before you evaluate anything.
- A matched rule is reported by its id in a list called `matched_rules`.
  (The Python API calls the same list `fired_rules`.)
- Endpoints marked **(login)** need a token in the `Authorization` header.

## Logging in

Create a user once, then ask for a token:

```bash
curl -X POST http://localhost:8000/api/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username": "alice", "email": "alice@example.com", "password": "Str0ng-Passw0rd!"}'

curl -X POST http://localhost:8000/api/v1/auth/token \
  -d "username=alice&password=Str0ng-Passw0rd!"
```

The token endpoint takes a form (`username=...&password=...`), not JSON. It
answers with:

```json
{"access_token": "eyJhbGciOi...", "token_type": "bearer", "role": "business"}
```

Send the token with every request marked **(login)**:

```bash
curl http://localhost:8000/api/v1/rules -H "Authorization: Bearer eyJhbGciOi..."
```

## Rules

### POST /api/v1/rules (login)

Store a new rule.

**Request:**
```json
{
  "name": "big_payment",
  "group": "payments",
  "priority": 10,
  "action": "review",
  "conditions": {"type": "condition", "field": "amount", "op": ">", "value": 1000}
}
```

- `name`, `conditions` and `action` are required.
- `group` collects rules into a rule set. Evaluate one group with `ruleset_id`
  (see below).
- `priority` orders the matches: higher numbers come first. It defaults to 0.
- `conditions` uses the condition format described in [Conditions](conditions.md).
- `evaluation_mode` (`"stateless"` by default) is stored and returned as a
  label only. No evaluation reads it: a rule marked `"stateful"` is evaluated
  like any other.

**Response:** the stored rule, with its new `id`, a `current_version` of 1
and timestamps.

Before storing it, the server checks the new rule against the rules already in
its group. If it finds a conflict, such as the same name or the same priority,
it answers `400` with the list of conflicts and keeps the rule aside for
review instead of storing it. Add `?skip_conflict_check=true` to store it
anyway. `POST /api/v1/rules/validate` runs the same check without storing
anything. See [Rule Analysis](rule-analysis.md).

### GET /api/v1/rules (login)

List the stored rules.

## Evaluating facts

### POST /api/v1/evaluate (login)

Evaluate one fact against the stored rules.

**Request:**
```json
{
  "facts": {"amount": 4200, "country": "DE"},
  "ruleset_id": "payments"
}
```

- `facts` is the fact to evaluate. Required.
- `ruleset_id` is optional. It limits the evaluation to the rules of that
  `group`. Without it, all stored rules are used.
- `rule_ids` is optional. It limits the evaluation to those rule ids, such as
  `[1, 4]`.

**Response:**
```json
{
  "execution_id": "8ac723da-c93d-40ec-809c-64a244003e9e",
  "ruleset_group": "payments",
  "matched_rules": [1, 2],
  "actions": ["review", "add_vat"],
  "facts": {"amount": 4200, "country": "DE"}
}
```

- `matched_rules`: the ids of the rules that matched, highest priority first.
- `actions`: their actions, in the same order. The server does not run them;
  the caller does.
- `execution_id`: an id for this evaluation. Use it with
  `GET /api/v1/explain/{execution_id}`.
- `ruleset_group`: the `ruleset_id` you sent, or `"all"`.

### POST /api/v1/evaluate/bulk (login)

Evaluate several facts against the same rules in one request.

**Request:**
```json
{
  "facts": [
    {"amount": 4200, "country": "DE"},
    {"amount": 50, "country": "US"}
  ],
  "ruleset_id": "payments"
}
```

`facts` is a list here. `ruleset_id` and `rule_ids` work as for a single fact.

**Response:**
```json
{
  "count": 2,
  "ruleset_group": "payments",
  "results": [
    {"index": 0, "execution_id": "1105cdb5-...", "matched_rules": [1, 2], "actions": ["review", "add_vat"]},
    {"index": 1, "execution_id": "9c24bea9-...", "matched_rules": [], "actions": []}
  ]
}
```

`results` has one entry per fact, in the order you sent them. `index` is the
position of the fact in your list.

### GET /api/v1/explain/{execution_id} (login)

Look up an earlier evaluation by its `execution_id`. The response has the same
fields as `POST /api/v1/evaluate`, including the facts that were evaluated. An
unknown id answers `404`.

The server keeps only the most recent records: 10,000 by default, set by the
`EXPLAIN_STORE_MAX_RECORDS` environment variable (`0` keeps none). An older
`execution_id` answers `404`. The records live in the server's memory, so
they are lost when it restarts, and with several server processes each one
has its own.

### POST /api/v1/rules/simulate (login)

Evaluate a fact as a dry run and get an explanation for each matched rule.

**Request:**
```json
{
  "event": {"amount": 4200, "country": "DE"},
  "rule_ids": [1, 2]
}
```

`event` is the fact. `rule_ids` is optional and limits the run to those rules.

**Response:**
```json
{
  "matched_rules": [
    {"id": 1, "name": "big_payment", "priority": 10},
    {"id": 2, "name": "german_payment", "priority": 0}
  ],
  "execution_order": [1, 2],
  "explanations": {
    "1": "Rule big_payment (1) matched via PHREAK (segments: seg_amount, seg_country)",
    "2": "Rule german_payment (2) matched via PHREAK (segments: seg_amount, seg_country)"
  },
  "dry_run": true,
  "stats": {
    "total_rules": null,
    "candidates_evaluated": 2,
    "rules_matched": 2,
    "evaluation_time_ms": 0.41,
    "optimization": null
  }
}
```

- `matched_rules`: each matched rule's id, name and priority, in the order
  they fired. `execution_order` lists the same ids.
- `explanations`: why each rule matched.
- `stats`: how many rules the engine looked at closely after filtering
  (`candidates_evaluated`), how many matched (`rules_matched`), and how long
  it took in milliseconds (`evaluation_time_ms`). `total_rules` and
  `optimization` are not filled in.

## Engine endpoints

These endpoints under `/api/v1/engines` need no login.

### POST /api/v1/engines/evaluate

Evaluate a fact against the stored rules and get an explanation for each
matched rule.

**Request:**
```json
{"event": {"amount": 4200, "country": "DE"}, "rule_ids": [1, 2]}
```

- `event` is the fact. Required.
- `rule_ids` is optional and limits the run to those rules.
- `engine_type` is optional. `"PHREAK"`, the only engine, is the default; any
  other name answers `400`.

**Response:**
```json
{
  "matched_rules": [
    {"id": 1, "name": "big_payment", "priority": 10},
    {"id": 2, "name": "german_payment", "priority": 0}
  ],
  "execution_order": [1, 2],
  "explanations": {
    "1": "Rule big_payment (1) matched via PHREAK (segments: seg_amount, seg_country)",
    "2": "Rule german_payment (2) matched via PHREAK (segments: seg_amount, seg_country)"
  },
  "stats": {"latency_ms": 1.68, "rules_evaluated": 2, "rules_matched": 2},
  "engine_type": "PHREAK",
  "dry_run": false
}
```

The fields are the same as for `POST /api/v1/rules/simulate`, except for the
names in `stats`: `rules_evaluated` is the number of rules the engine looked at
closely after filtering, and `latency_ms` is the time taken.

### POST /api/v1/engines/simulate

The same request and response as `/api/v1/engines/evaluate`, with
`"dry_run": true`. Neither endpoint runs actions or changes anything, so the
two give the same answers.

### GET /api/v1/engines/config and GET /api/v1/engines/available

Report the engine in use and the engines available (only `"PHREAK"`), with a
short description of each.

### Endpoints that are not finished

These endpoints answer, but do not yet do what their names say:

- `POST /api/v1/engines/switch` and `POST /api/v1/engines/reload` check the
  engine name and answer `"status": "success"`, but change nothing on the
  server. Without Redis, rules stored with `/api/v1/rules` are used from the
  next request on. With Redis, these engine endpoints (and
  `/api/v1/rules/simulate`) read the rule list from a Redis cache that lasts up
  to 5 minutes, so a new or changed rule can take that long to appear there.
  `/api/v1/evaluate` always reads the stored rules directly.
- `POST /api/v1/engines/benchmark` times a new engine with no rules loaded on
  generated events, so it does not measure your rules.
- `GET /api/v1/engines/stats` reports a new engine with no rules loaded, so
  `rules_loaded` is always `0`.

## Checking a rule set

### POST /validate

Check a rule set for problems without storing it. No login needed.

**Request:**
```json
{
  "ruleset": {
    "group": "payments",
    "rules": [
      {
        "id": 1,
        "name": "big_payment",
        "conditions": {"type": "condition", "field": "amount", "op": ">", "value": 1000}
      }
    ]
  }
}
```

**Response:**
```json
{"issues": []}
```

`issues` lists each problem as a sentence, such as `"Ruleset is empty"`. An
empty list means the rule set is fine. A condition the server cannot read at
all, such as an unknown operator, answers `422` instead (see
[Errors](#errors)).

## Sessions

Sessions store facts on the server under a session id, so you can collect
facts over several requests and evaluate them later. A session holds at most
100 facts and is visible only to the user who created it.

Sessions live in the memory of one server process. They are lost when the
server restarts, and if you run several server processes, each one has its
own sessions: send all requests for a session to the same process.

### POST /api/v1/sessions (login)

Create a session.

**Request:**
```json
{"metadata": {"channel": "web"}}
```

Both fields are optional. `metadata` is any data you want to keep with the
session. `session_id` lets you choose the id yourself; otherwise the server
makes one.

**Response (`201`):**
```json
{
  "id": "a43cdf91-61f3-41ac-a55d-526d6e806ab6",
  "user_id": 1,
  "metadata": {"channel": "web"},
  "fact_count": 0,
  "created_at": "2026-10-31T23:19:46.484674Z",
  "updated_at": "2026-10-31T23:19:46.484674Z"
}
```

### POST /api/v1/sessions/{id}/facts (login)

Add a fact to a session.

**Request:**
```json
{"fact_id": "txn_123", "fact": {"amount": 5000}}
```

`fact` is the fact. `fact_id` is optional; sending the same `fact_id` again
replaces that fact.

### POST /api/v1/sessions/{id}/evaluate (login)

Evaluate every fact stored in the session against the stored rules. Each fact
is evaluated **on its own**, and you get one result per fact. Facts are never
combined, so two transactions with the same fields each get their own answer.

**Request** (optional; send no body to use all stored rules):
```json
{"ruleset_id": "payments"}
```

`ruleset_id` and `rule_ids` work as for `POST /api/v1/evaluate`.

**Response:**
```json
{
  "session_id": "a43cdf91-61f3-41ac-a55d-526d6e806ab6",
  "count": 2,
  "ruleset_group": "payments",
  "results": [
    {"index": 0, "fact_id": "txn_1", "execution_id": "1105cdb5-...", "matched_rules": [1, 2], "actions": ["review", "add_vat"]},
    {"index": 1, "fact_id": "txn_2", "execution_id": "9c24bea9-...", "matched_rules": [], "actions": []}
  ]
}
```

- `results` are in the order the facts were first added. Replacing a fact
  (sending the same `fact_id` again) keeps its place.
- `fact_id` says which stored fact each result belongs to.
- Each `execution_id` works with `GET /api/v1/explain/{execution_id}`.

The answers are the same as sending the facts to `POST /api/v1/evaluate/bulk`.
Evaluating only reads the session: its facts stay as they were.

Also available: `GET /api/v1/sessions/{id}` and `GET /api/v1/sessions/{id}/facts`
to read a session back, `DELETE /api/v1/sessions/{id}/facts/{fact_id}` to
remove one fact, and `DELETE /api/v1/sessions/{id}` to remove the session.

## Server health

### GET /health

Answers `{"status": "healthy"}` while the server runs. No login needed.

### GET /api/v1/system/status

The version and the state of each part of the server. No login needed.

```json
{
  "status": "running",
  "version": "1.1.1",
  "engine": "fluxrules",
  "healthy": true,
  "components": {
    "queue": {"healthy": true, "message": "Queue not configured (embedded mode)"},
    "cache": {"healthy": true, "message": "Cache not configured (embedded mode)"},
    "persistence": {"healthy": true, "message": "Persistence is healthy"}
  }
}
```

## Errors

Most errors use FastAPI's format, with the reason under `detail`:

```json
{"detail": "Execution 'abc' not found"}
```

A request whose body has the wrong shape answers `422`, and `detail` lists each
problem with its location:

```json
{
  "detail": [
    {"type": "missing", "loc": ["body", "facts"], "msg": "Field required", "input": {"fact": {}}}
  ]
}
```

Errors raised by the rule engine itself use an `error` code and a `message`:

```json
{"error": "DSL_PARSE_ERROR", "message": "..."}
```

Status codes you will see:

- `400`: the request was understood but refused, for example a rule conflict.
- `401`: the token is missing, wrong or expired.
- `404`: the rule, session or execution does not exist.
- `422`: the request body has the wrong shape.
- `500` or `503`: a problem on the server, such as the database being
  unavailable.
