    Conditions & Rule Authoring¶

    A rule's conditions field defines when the rule fires. FluxRules gives you four ways to author conditions, the same condition tree on the wire for all four, and a set of tools to validate before you deploy.

    Start with Authoring Rules for how to choose between them. This page is the reference: every operator and every validation tool.

    Four ways to write conditions¶

    1. F DSL (recommended for Python code)¶

    Write conditions as natural Python expressions using the F helper. Each expression compiles to a condition dict the engine accepts; you never touch raw dicts.

    from fluxrules import F, Rule

# Single leaf
rule = Rule(
    name="high_value",
    conditions=F("amount") > 5000,
    action="review",
)

# AND: both must hold
rule = Rule(
    name="high_value_us",
    conditions=(F("amount") > 5000) & (F("country") == "US"),
    action="review",
)

# OR: either suffices
rule = Rule(
    name="risky_origin",
    conditions=(F("country").isin(["NG", "SN"])) | (F("ip_risk_score") >= 70),
    action="block",
)

# NOT
rule = Rule(
    name="unverified",
    conditions=~F("verified").exists(),
    action="step_up",
)

# Composed
rule = Rule(
    name="fraud_triage",
    conditions=(
        (F("amount") > 2000)
        & (F("payment_method").isin(["crypto", "prepaid_card"]))
        & (
            (F("country").isin(["NG", "SN", "GH"]))
            | (F("ip_risk_score") >= 70)
        )
        & ~(F("email_domain").ends_with("trusted.example"))
    ),
    action="manual_review",
)

    Operator precedence warning. Python's & and | bind more tightly than comparisons like >, <, ==. Always wrap each individual condition in parentheses:

    # python skip: the second line deliberately raises to show the trap
# Correct
(F("amount") > 5000) & (F("country") == "US")

# Wrong: & binds before ==, raising a TypeError at runtime
F("amount") > 5000 & F("country") == "US"

    2. Dict / YAML (for config-driven rules)¶

    The dict format is the wire and storage format. Use it when rules come from a database, YAML file, or API response.

    Rule(
    name="high_value",
    conditions={"type": "condition", "field": "amount", "op": ">", "value": 5000},
    action="review",
)

    YAML (loaded with load_rules_from_yaml, see YAML Rules):

    name: high_value
conditions:
  type: condition
  field: amount
  op: ">"
  value: 5000
action: review

    AND/OR in dict form:

    {
    "type": "group",
    "op": "AND",
    "children": [
        {"type": "condition", "field": "amount", "op": ">", "value": 5000},
        {"type": "condition", "field": "country", "op": "==", "value": "US"},
    ],
}

    The F DSL and the dict format describe the same conditions. Mix them freely: a Rule built with F(...) stores a dictionary tree like one built from a dict, and loads back from YAML the same way. One difference in shape: a & b & c nests as (a & b) & c, where a hand-written dict usually has one flat group of three. Both give the same results.

    3. RuleBuilder (fluent, step by step)¶

    RuleBuilder chains method calls and validates each step. Useful when building rules programmatically where you want to catch errors early.

    from fluxrules import F, RuleBuilder

rule = (
    RuleBuilder()
    .name("high_value_us")
    .priority(10)
    .condition((F("amount") > 5000) & (F("country") == "US"))
    .action("review")
    .build()
)

    .condition() accepts both an F expression and a raw dict.

    4. Checked field references with fields(Model)¶

    When your facts have a model, such as a Pydantic class, you can name fields through the model instead of typing them as strings. fields(Model) gives an object whose attributes are the model's fields:

    from pydantic import BaseModel

from fluxrules import F, Rule
from fluxrules.facts import fields


class Account(BaseModel):
    age_days: int
    country: str


class Payment(BaseModel):
    amount: float
    account: Account


p = fields(Payment)

rule = Rule(
    name="block_high_risk_country",
    conditions=p.account.country.isin(["NG", "RU"]) & (p.amount > 1000),
    action="block",
)

    Read the condition piece by piece:

    • p.amount is the same as F("amount").
    • p.account.country is the same as F("account.country"). A nested model becomes a dotted field name, which is how the engine sees nested facts.
    • .isin(["NG", "RU"]) and > 1000 are the ordinary F operators, so every operator on this page works here too.
    • & joins the two parts with AND. The comparison is wrapped in parentheses, as with F. The isin(...) call needs none, because a method call binds before &.

    The rule stores the same condition tree as one written with F:

    written_with_f = F("account.country").isin(["NG", "RU"]) & (F("amount") > 1000)
assert rule.conditions == Rule(name="same", conditions=written_with_f, action="block").conditions

    The difference is when a typo is caught. F("acount.country") is accepted and the rule never matches. p.acount raises UnknownFieldError on that line, and the message suggests account:

    from fluxrules import UnknownFieldError

try:
    p.acount  # noqa: B018
except UnknownFieldError as exc:
    assert "Did you mean 'account'?" in str(exc)

    dir(p.account) lists the fields, so an editor can offer them as you type. See Typed Facts.

    All available operators¶

    Comparison (Python dunders)¶

    F expression Dict "op" Meaning
    F("x") == v "==" or "eq" Equal
    F("x") != v "!=" or "ne" Not equal
    F("x") > v ">" or "gt" Greater than
    F("x") >= v ">=" or "gte" Greater than or equal
    F("x") < v "<" or "lt" Less than
    F("x") <= v "<=" or "lte" Less than or equal

    The six comparison operators also accept their word-form aliases in dict/YAML (eq, ne, gt, gte, lt, lte), normalised before evaluation.

    Collection membership¶

    F expression Dict "op" Meaning
    F("x").isin(["a", "b"]) "in" Value is a member of the list
    F("x").not_in(["a"]) "not_in" Value is not a member

    String / collection containment¶

    F expression Dict "op" Meaning
    F("x").contains("tag") "contains" Collection or string contains value
    F("x").not_contains("flag") "not_contains" Does not contain

    String matching¶

    Both sides are coerced to strings before matching.

    F expression Dict "op" Meaning
    F("x").starts_with("adm") "starts_with" str(x).startswith(...)
    F("x").ends_with(".com") "ends_with" str(x).endswith(...)
    F("x").regex("^4[0-9]{12}") "regex" re.search(pattern, str(x)). It matches anywhere in the string, so add ^ to anchor at the start

    Boolean composition (F DSL)¶

    Operator Meaning Dict equivalent
    a & b AND {"type": "group", "op": "AND", "children": [a, b]}
    a \| b OR {"type": "group", "op": "OR", "children": [a, b]}
    ~a NOT {"type": "not", "condition": a}

    Field presence¶

    F("email").exists()          # True when "email" key is in facts and not None
~F("email").exists()         # True when "email" is absent or None

    Dict equivalent:

    {"type": "exists", "field": "email"}

    Use exists() when a field might legitimately be absent. A condition node raises FieldNotFoundError if a present key is the same field spelled differently (see Field names are exact). exists() never raises.

    What to keep in mind when authoring rules¶

    Field names are exact¶

    F("Amount"), F("amount") and F("user_age") / F("userAge") are different fields: the engine reads the exact key. When a rule's field is missing from a fact but the fact has a key that looks like the same field, the engine raises FieldNotFoundError instead of quietly not matching. What counts as a look-alike depends on whether the engine has a fact schema:

    Engine Look-alikes that raise Example
    No schema Case only Amount against amount
    fact_schema=Model Case and key style: _, - and spaces are ignored user_age against userAge, user-age or UserAge

    Without a schema, one ruleset may serve several kinds of facts that spell a field differently (user_id from one system, userId from another). The engine cannot tell that apart from a typo, so it only treats case as a typo. With a schema, every rule field is checked against the model when the rules load, so a key in another style can only be a mismatch.

    In both cases a . is significant, because it separates levels of nesting: user.name is never a look-alike of username. A dotted field such as user.age against an unflattened {"user": {...}} raises too, with a hint to flatten the fact (see Nested Facts). A field that is absent with no look-alike returns False. Numbered families stay distinct: field_0 is not a look-alike of field_10.

    # python skip: the first line deliberately raises to show the check
# Fact: {"amount": 5000, "user_age": 30}, engine without a schema
F("Amount") > 1000    # raises FieldNotFoundError: did you mean 'amount'?
F("userAge") >= 18    # no match (with a schema it would raise)
F("amount") > 1000    # evaluates correctly

    A schema also catches these before any fact arrives: load_rules rejects any rule field the model lacks.

    Operator precedence: always use parentheses¶

    Python evaluates & and | before >, <, ==. The rule is simple: wrap every individual F(...) comparison in its own parentheses before composing:

    # python skip: the unsafe line deliberately raises to show the trap
# safe: each leaf is wrapped
(F("amount") > 5000) & (F("country") == "US")

# unsafe: raises TypeError
F("amount") > 5000 & F("country") == "US"

    Use exists() for optional fields¶

    A condition node on a field that is absent raises (if the name looks like a typo) or returns False (if genuinely different schema). When a field is intentionally optional, guard it with exists():

    # Only fires if "promo_code" is present AND matches
F("promo_code").exists() & (F("promo_code") == "SUMMER24")

    Missing fields and NOT¶

    A condition on a missing field is False, so NOT over it is True: ~(F("blocked") == True) fires on a fact with no blocked key. That is rarely what the rule means, and a key sent under another name (is_blocked) lets the rule through silently.

    EngineConfig.missing_field sets how NOT treats a missing field:

    missing_field ~(F("blocked") == True) on {"amount": 1} Notes
    None (default) fires, and emits MissingFieldNotWarning once 1.x behaviour with a heads-up
    "false" fires 1.x behaviour, no warning
    "unknown" does not fire the 2.0 default

    With "unknown" a missing field is unknown, as SQL treats NULL: NOT of unknown is unknown, AND / OR follow three-valued logic, and a rule fires only when its condition is definitely true. exists() is never unknown, so it is the way to test for absence on purpose:

    from fluxrules import EngineConfig, F, Rule
from fluxrules.engine.phreak import PhreakEngine

engine = PhreakEngine(config=EngineConfig(missing_field="unknown"))
engine.load_rules(
    [
        Rule(id=1, name="not_blocked", conditions=~(F("blocked") == True), action="allow"),  # noqa: E712
        # Explicit: "blocked is absent, or present and not True"
        Rule(
            id=2,
            name="not_blocked_or_absent",
            conditions=~F("blocked").exists() | ~(F("blocked") == True),  # noqa: E712
            action="allow",
        ),
    ]
)
assert engine.evaluate({"amount": 1}).fired_rules == [2]
assert sorted(engine.evaluate({"blocked": False}).fired_rules) == [1, 2]

    The setting applies to PhreakEngine (interpreted and compiled) and to fluxrules.evaluate(), which reads the process-wide config (fluxrules.engine.configuration.set_config). Set it before load_rules: compiled conditions read it when they are compiled.

    Value types must match¶

    A numeric field compared with a string will not raise, but will silently not match. Match the value type to the field type:

    F("amount") > 5000      # number field → number value
F("status") == "active" # string field → string value
F("tags").contains("vip")  # list field → scalar value to find in it

    isin takes a list, not positional args¶

    # python skip: the second line deliberately raises to show the trap
F("country").isin(["NG", "SN", "GH"])   # correct
F("country").isin("NG", "SN", "GH")    # wrong: TypeError

    Combining AND chains cleanly¶

    For long AND chains, align the & operators at the start of each line:

    conditions=(
    (F("amount") > 2000)
    & (F("payment_method").isin(["crypto", "prepaid_card"]))
    & (F("chargeback_ratio") >= 0.1)
    & ~(F("email_domain").ends_with("trusted.example"))
),

    Validation¶

    FluxRules validates condition trees at rule construction time (Pydantic) and exposes an explicit validate step for bulk checks before deployment.

    Automatic validation at construction¶

    Invalid conditions are caught when you build the Rule:

    # python skip: this block deliberately raises to show the validation error
from fluxrules import F, Rule

Rule(
    name="bad",
    conditions={"type": "condition", "field": "x", "op": "???", "value": 1},
    action="flag",
)
# raises ConditionValidationError: unknown operator '???'

    Missing required keys, unknown operators, and malformed tree shapes all raise ConditionValidationError immediately.

    validate(): check a batch without evaluating¶

    from fluxrules import F, Rule, validate

rules = [
    Rule(name="r1", conditions=F("amount") > 5000, action="flag"),
    Rule(name="r2", conditions=F("status") == "active", action="allow"),
]

issues = validate(rules)
if issues:
    for issue in issues:
        print(issue)
else:
    print("All rules valid")

    validate() returns a list of human-readable strings. An empty list means all rules passed. Use it in CI before deploying a new ruleset.

    FieldNotFoundError at evaluation time¶

    When a condition field is absent from the incoming fact and the name is a case variant of a present key (e.g. Amount vs amount), the engine raises instead of silently returning False:

    from fluxrules import F, FieldNotFoundError, Rule, evaluate

rule = Rule(name="r", conditions=F("Amount") > 5000, action="flag")
try:
    evaluate(rule, {"amount": 6000})
except FieldNotFoundError as e:
    print(e)
# Field 'Amount' not found in fact. Did you mean 'amount'? Available keys: ['amount']

    To deliberately test whether a field is present before comparing its value, use F("field").exists():

    # Does not raise even when "score" is absent
F("score").exists() & (F("score") >= 90)

    Full validation example¶

    from fluxrules import F, Rule, validate

rules = [
    Rule(
        name="fraud_check",
        conditions=(
            (F("amount") > 10000)
            & (F("country").isin(["NG", "SN", "GH"]))
            & ~(F("verified").exists())
        ),
        action="block",
        priority=10,
    ),
    Rule(
        name="vip_fast_track",
        conditions=(F("tier") == "gold") | (F("spend_ytd") >= 50000),
        action="expedite",
        priority=5,
    ),
]

issues = validate(rules)
assert issues == [], issues

from fluxrules import evaluate

fact = {"amount": 15000, "country": "NG"}
result = evaluate(rules, fact)
print(result.fired_rules)   # rule ids that matched
print(result.actions)       # ["block"]

    Condition tree reference¶

    The dict / YAML format uses these node shapes:

    Node type Required keys Optional keys
    condition type, field, op, value none
    group / and / or type, children (or conditions) op (default AND)
    not type, condition none
    exists type, field none

    Accepted aliases: "and", "or", "not", "exists", "group", "composite".
